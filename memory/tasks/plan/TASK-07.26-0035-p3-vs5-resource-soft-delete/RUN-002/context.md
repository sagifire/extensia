## Мета run

Реалізувати точне м'яке видалення лише листка й типову невидимість: публічні помилки, підготовлений набір цільового Resource та сусідів, збереження tombstone, щільну переіндексацію зі спільною часовою міткою, фільтрацію читання, перевірку цілісності, матриці конкурентності, аварій, відновлення й попереджень, повні та пакетні gates і незалежний аудит без відкритих P0-P3.

## Ефективні вимоги

- Публічний контракт і facade мають надати точні `deleteResource(id)` та `ResourceDeleteError`; повторне видалення має бути єдиним кодом, специфічним для tombstone.
- Домен і Core мають реалізувати допустимість видалення листка, перехід у tombstone, нормалізацію активних сусідів джерела й точний підготовлений набір цільового Resource та сусідів.
- Читання й індекс мають типово приховувати tombstone у пошуку за id, списку, дітях і дереві та перевіряти пакет; команда все ще може повернути відокремлений tombstone.
- Протокол і відновлення мають додати `resource.delete`, одну семантичну фіксацію й один запис, початкову перевірку active-parent/order/visibility та повторно використати стики integrity і життєвого циклу VS3.
- Відсутній активний цільовий Resource дає `RESOURCE_NOT_FOUND`; tombstone дає `RESOURCE_ALREADY_DELETED`; будь-яка активна дитина дає `RESOURCE_HAS_CHILDREN`.
- Випадки root/non-root і першого, середнього, останнього чи єдиного сусіда мають забезпечувати щільну переіндексацію джерела.
- Цільовий Resource зберігає parent/order/locked/hidden/Marks/KV та змінює тільки прапорець видалення і спільну часову мітку.
- `locked` і `hidden` не блокують і не змінюють поведінку; типові get/list/children/tree приховують tombstone, а update/move/Marks/KV для нього повертають `RESOURCE_NOT_FOUND`.
- Некоректні й неефективні операції не створюють транзакції чи журналу; ефективне видалення готує точний змінений набір, відсортований за id, з однією часовою міткою, однією фіксацією й одним записом.
- Пошкоджена активна дитина tombstone або відсутнього parent, дублікат чи прогалина order або видимий tombstone є типізованою integrity-помилкою, блокує готовність і переводить runtime у fail-close.
- Синхронізація пам'яті охоплює фактичну поточну реалізацію й поведінку читання, технічну архітектуру або стек, якщо потрібно, а також task/run/result/progress/state/indexes; target/product лишаються `not-needed`, якщо немає погодженого виправлення.
- Результат має зафіксувати мовний контроль, архітектурний тиск, стани загального рівня, ризики й незалежний аудит.

## Ризики

- Існування tombstone може витекти через типові проєкції читання чи запитів або відображення помилок.
- Нормалізація сусідів чи спільна часова мітка можуть бути неповними.
- Видалення може помилково дозволити активних дітей.
- Попередження publish/cleanup після фіксації може неправильно перетворити зафіксоване видалення на відмову.
- Реалізація може створити новий шлях повноважень запису чи індексу замість повторного використання стиків VS3.
