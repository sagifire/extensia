# Контекст виконання: RUN-002

## Мета run

Реалізувати прийняту повну заміну Marks і заміну або видалення простору імен KV поверх стабілізованих стиків VS3: точний, безпечний щодо дескрипторів розбір `setMarks`/`setKV`, обмеження, канонічне впорядкування, поведінку без змін, публічні типи й помилки, конвеєр одного Resource, журнал, fingerprint, відновлення та відокремлене читання назад із пакета.

## Ефективні вимоги

- Публічні кореневі та facade-контракти мають надати точні `SetMarkInput`, `setMarks`, `setKV`, експорти й адаптери `ResourceMarksError`/`ResourceKVError` без додаткових кодів.
- Допоміжні засоби розбору й домену мають безпечно щодо дескрипторів розбирати щільні масиви та точні звичайні записи або записи з null-прототипом, канонічно сортувати Marks і ключі та перевіряти рівність і обмеження.
- Обробник Core має використовувати одне блокування цільового Resource, завантаження найновішого стану, повну заміну або випадок без змін, власний `updated_at`, підготовлений набір одного Resource та наявні стики семантичної фіксації, індексу й читання назад.
- Об'єднання протоколу й тести мають додати `resource.marks.set` і `resource.kv.set`, повторно використовуючи підготовлений набір VS3 та незмінне відображення integrity-помилок.
- Marks: щільний `Array` не більше 256 елементів; дозволені лише data properties довжини та індексів; елемент має рівно власні перелічувані `type/name/value`; рядки непорожні й завдовжки 1..128; value має тип int32 або null; дублікат `(type,name)` дає `RESOURCE_INPUT_INVALID`; застосовується бінарне сортування `(type,name)`; порожній вхід очищає Marks.
- KV: простір імен і ключ непорожні й завдовжки 1..128; потрібен точний перелічуваний звичайний запис або запис із null-прототипом; дозволено не більше 256 ключів і результуючих просторів імен; довжина value 0..16384; сума `sum(namespace.length+key.length+value.length)` не перевищує 1,048,576; порожній запис видаляє простір імен; порядок ключів ігнорується.
- Відсутній або видалений цільовий Resource дає `RESOURCE_NOT_FOUND`; помилка входу чи обмеження дає `RESOURCE_INPUT_INVALID`; точна рівність дає `RESOURCE_NO_CHANGES`; readonly перевіряється до інспекції; діє точний пріоритет блокування, I/O та integrity з розділу 11.
- Ефективна зміна модифікує лише Marks або цільовий простір імен та власну часову мітку, створює одну фіксацію й один запис і повертає успішний відокремлений цільовий Resource із читанням назад.
- Синхронізація пам'яті охоплює фактичний поточний стан домену й технічний стан реалізації, якщо потрібно, а також task/run/result/progress/state/indexes; канонічні target/product зазвичай мають стан `not-needed`.
- Результат має зафіксувати стани загального рівня, мовний контроль, архітектурний тиск, подальші дії без активації, ризики й незалежний аудит.

## Критерії приймання

- [ ] Точний публічний розбір, типи, експорти, адаптери й помилки реалізовані без зайвих кодів.
- [ ] Ворожі дескриптори, accessors, symbols, успадковані й неперелічувані поля, розріджені масиви та прототипи покриті.
- [ ] Для Marks перевірені точні обмеження рядків, кількості й int32, дублікати, бінарний порядок та очищення порожнім входом на межах ±1.
- [ ] Для KV перевірені точні обмеження простору імен, ключа, value, кількості й суми, результуючі простори імен, видалення порожнім записом і рівність незалежно від порядку властивостей на межах ±1.
- [ ] Відсутність, видалення, некоректний вхід і випадок без змін дають точні помилки, readonly перевіряється до інспекції, а некоректна чи неефективна операція не створює транзакції або журналу.
- [ ] Ефективний запис змінює тільки дозволений aggregate та власну часову мітку й має одну семантичну фіксацію та один запис.
- [ ] Перевірені FIFO для Marks і KV одного Resource, різні Resources та розклади сукупного запису проти зміни сусіда в ієрархії.
- [ ] Перевірені точки begin/stage/commit/publish/cleanup, аварійні сценарії та відновлення у свіжому процесі.
- [ ] Знімки успішної відповіді й читання назад відокремлені, а API пакета точний.
- [ ] Цільові тести, `npm run check`, перевірки пакета, типів і packed consumer, `git diff --check` та сканування джерел зелені й мають точні докази.
- [ ] Незалежний аудит завершено без відкритих P0-P3.
- [ ] Повністю зафіксовані синхронізація пам'яті, мовний контроль, архітектурний тиск, ризики й стан подальших дій.
- [ ] Активація відбувається лише за окремим прямим рішенням користувача.
