# Extensia

## Domain Model v2

> Статус: draft  
> Призначення: зафіксувати чисту предметну модель Extensia без домішки runtime-архітектури, API-фасадів і механіки розширення.

# 1. Межі документа

Цей документ описує тільки предметну модель Extensia:

* основні доменні сутності
* їхні властивості
* відношення між сутностями
* інваріанти моделі
* семантику прапорів стану
* канонічні TypeScript-контракти доменних даних

У цьому документі свідомо не описуються:

* системне ядро
* драйвери сховища
* журнал операцій
* асинхронна система замків
* гарячі індекси
* синхронізація між процесами
* система плагінів
* фасади публічного API
* життєвий цикл запуску бібліотеки
* реалізація гарантій атомарності, узгодженості, ізольованості та довговічності

Ці частини належать до окремих документів архітектурного і інтеграційного рівня.

# 2. Ubiquitous Language

## 2.1. Resource

**Resource** — базова доменна сутність, яка представляє логічну одиницю контенту у вигляді об’єкта з метаданими.

Resource є центром предметної моделі. Саме навколо нього групуються всі інші доменні дані:

* asset-об’єкти
* marks
* kv-дані
* зв’язки з дочірніми ресурсами

## 2.2. Asset

**Asset** — доменна сутність, що представляє метадані файлу ресурсу та його дескриптор.

Є два допустимі варіанти asset:

* **internal asset** — представляє файл, що належить сховищу Extensia; у цьому випадку ідентифікатор asset виступає логічним дескриптором файлу
* **external asset** — представляє зовнішній файл ресурсу через поле `url`

Asset завжди належить рівно одному Resource.

## 2.3. Mark

**Mark** — іменована мітка ресурсу, яка складається з:

* `type` — категорії або простору класифікації
* `name` — назви мітки
* `value` — необов’язкового числового значення ваги

Mark використовується для класифікації, фільтрації, ранжування та інших прикладних сценаріїв, де потрібна компактна типізована ознака.

## 2.4. KV

**KV** — дворівневий словник довільних рядкових атрибутів ресурсу у формі:

`namespace -> key -> string value`

KV призначений для прикладних і службових атрибутів, які не мають бути частиною жорсткої доменної схеми.

## 2.5. Resource tree

**Resource tree** — деревовидна ієрархія ресурсів, що формується через поле `parent_id`.

У моделі Resource може мати:

* нуль батьківських ресурсів
* або рівно один батьківський ресурс

Список дочірніх ресурсів є похідною проєкцією і не є джерелом істини.

# 3. Основні доменні сутності

## 3.1. Resource

Resource представляє логічну одиницю контенту та агрегує навколо себе всі пов’язані дані.

На рівні домену Resource:

* має власні метадані
* володіє asset-об’єктами
* містить marks
* містить KV-дані
* може бути вузлом деревовидної ієрархії ресурсів

### Семантика основних полів Resource

#### `id`
Унікальний ідентифікатор ресурсу в межах сховища.

#### `created_at`
Мітка часу створення ресурсу.

#### `updated_at`
Мітка часу останньої зміни метаданих ресурсу або його підлеглих доменних даних, якщо така політика оновлення застосовується інтеграцією.

#### `title`
Коротка назва ресурсу.

#### `description`
Довший текстовий опис ресурсу або `null`, якщо опис відсутній.

#### `parent_id`
Ідентифікатор батьківського ресурсу або `null`, якщо ресурс є кореневим.

#### `order_index`
Порядковий індекс ресурсу відносно його sibling-групи в межах одного батька.

#### `is_deleted`
Доменний прапор стану, який означає, що ресурс позначений як видалений.

#### `locked`
Зарезервований прапор для інтеграцій і розширень. Базовий функціонал бібліотеки не надає цьому полю прикладної поведінки.

#### `hidden`
Зарезервований прапор для інтеграцій і розширень. Базовий функціонал бібліотеки не надає цьому полю прикладної поведінки.

## 3.2. Asset

Asset представляє конкретний файловий або зовнішній носій даних ресурсу.

На рівні домену Asset:

* завжди належить рівно одному Resource
* описує один файл або одне зовнішнє посилання
* може бути позначений як primary asset ресурсу
* може посилатися на інший asset через `derived_from`

### Семантика основних полів Asset

#### `id`
Унікальний ідентифікатор asset у межах сховища.

Для internal asset це також логічний дескриптор файлу у сховищі. Сам asset не зобов’язаний містити фізичний шлях до файлу.

#### `type`
Вільний класифікаційний рядок, що описує загальний тип asset, наприклад `image`, `audio`, `video`, `link`.

#### `role`
Вільний класифікаційний рядок, що описує функціональну роль asset у межах ресурсу, наприклад `original`, `preview`, `thumbnail`.

#### `mime`
MIME-тип файлу або `null`, якщо він невідомий або не застосовується.

#### `extension`
Розширення файлу або `null`, якщо воно невідоме або не застосовується.

#### `is_external`
Прапор, який визначає природу asset:

* `false` — asset описує внутрішній файл сховища
* `true` — asset описує зовнішній файл через `url`

#### `is_primary`
Прапор, який означає, що asset є основним для ресурсу.

#### `is_on_uploading`
Прапор, який означає, що внутрішній файл asset перебуває у процесі завантаження або оновлення.

#### `url`
URL зовнішнього файлу для external asset.

Для internal asset це поле завжди `null`.

#### `derived_from`
Необов’язкове посилання на інший asset, від якого поточний asset був утворений або логічно походить.

Бажано, щоб це посилання вказувало на asset того самого Resource, але для базового функціоналу бібліотеки це не є жорсткою вимогою.

#### `created_at`
Мітка часу створення asset.

#### `updated_at`
Мітка часу останньої зміни метаданих або файлового стану asset.

#### `data`
Довільний об’єкт додаткових метаданих asset або `null`.

Це поле призначене для локальних даних asset і не замінює marks або resource-level KV.

## 3.3. Mark

Mark є компактною типізованою ознакою ресурсу.

### Семантика полів Mark

#### `type`
Категорія або простір класифікації мітки.

#### `name`
Назва конкретної мітки всередині категорії `type`.

#### `value`
Необов’язкове числове значення мітки.

Допустимі значення:

* `null`
* 32-бітне знакове ціле число

## 3.4. KV

KV є відкритою моделлю ресурсних атрибутів у формі словника:

* верхній рівень — namespace
* другий рівень — key
* значення — string

KV застосовується для:

* довільних прикладних атрибутів
* службових даних інтеграції
* даних, які не потребують окремої типізованої доменної сутності

### Межа між Mark і KV

Важливо розділяти ці дві моделі:

* **Mark** — для компактної класифікації, ваг, оцінок, фільтрації та ранжування
* **KV** — для довільних атрибутів, службових даних і розширених прикладних описів

# 4. Доменні відношення

## 4.1. Resource -> Asset

* один Resource може мати нуль або більше asset-об’єктів
* кожен Asset належить рівно одному Resource
* asset не може бути спільним для кількох ресурсів

## 4.2. Resource -> Resource

* один Resource може мати нуль або один `parent_id`
* один Resource може мати нуль або більше дочірніх ресурсів
* список дітей є похідною проєкцією, що формується через зворотний пошук по `parent_id`

## 4.3. Resource -> Mark

* один Resource може мати нуль або більше marks
* у межах одного Resource не допускаються дублікати `type + name`

## 4.4. Resource -> KV

* один Resource може мати нуль або більше namespace-груп KV
* у межах одного namespace ключі мають бути унікальними

## 4.5. Asset -> Asset

* Asset може мати `derived_from = null`
* або може посилатися на інший Asset
* таке посилання є слабким доменним зв’язком походження, а не окремим механізмом володіння

# 5. Інваріанти предметної моделі

## 5.1. Інваріанти Resource

1. `Resource.id` є унікальним у межах сховища.
2. Resource може мати не більше одного батька.
3. Якщо `parent_id = null`, Resource вважається кореневим.
4. Ієрархія ресурсів є деревом, тому циклічні зв’язки між Resource недопустимі.
5. `children[]`, якщо використовується у view-моделі, є похідною проєкцією, а не джерелом істини.
6. `is_deleted` є доменним прапором стану.
7. `locked` і `hidden` не мають обов’язкової базової поведінки в ядрі бібліотеки і трактуються як зарезервовані розширювальні прапори.

## 5.2. Інваріанти Asset

1. `Asset.id` є унікальним у межах сховища.
2. Asset належить рівно одному Resource.
3. У межах одного Resource може існувати не більше одного asset з `is_primary = true`.
4. Якщо `is_external = true`, то:
   * `url != null`
   * `is_on_uploading = false`
5. Якщо `is_external = false`, то:
   * `url = null`
6. `derived_from`, якщо задано, є посиланням на інший asset, але не створює окремого права володіння або вкладення.
7. Посилання `derived_from` бажано спрямовувати на asset того самого Resource, але це не є жорстким інваріантом базової моделі.

## 5.3. Інваріанти Mark

1. У межах одного Resource пара `type + name` є унікальною.
2. `value` може бути лише `null` або 32-бітним знаковим цілим числом.

## 5.4. Інваріанти KV

1. KV зберігається у формі `namespace -> key -> string value`.
2. У межах одного namespace кожен key є унікальним.
3. Значення KV завжди є рядком.

# 6. Семантика прапорів стану

## 6.1. Resource

У Resource немає складної машини станів.

Прапори `is_deleted`, `locked`, `hidden` працюють як незалежні поля:

* `is_deleted` є частиною доменної моделі
* `locked` і `hidden` зарезервовані для поведінки, яку може вводити інтеграція або плагінний шар

Базовий функціонал бібліотеки не визначає жорсткої логіки переходів для `locked` і `hidden`.

## 6.2. Asset

У Asset також немає складної машини станів. Його стан задається набором незалежних прапорів і полів із кількома обов’язковими зв’язками між ними.

### Допустима семантика для internal asset

При створенні internal asset:

* `is_external = false`
* `url = null`
* `is_on_uploading = true`

Після завершення завантаження файлу:

* `is_on_uploading = false`

Якщо файл asset пізніше оновлюється, `is_on_uploading` може знову тимчасово переходити в `true` на час повторного завантаження.

### Допустима семантика для external asset

Для external asset:

* `is_external = true`
* `url != null`
* `is_on_uploading = false`

# 7. Канонічні TypeScript-контракти доменних даних

```ts
export type IDString = string
export type Timestamp = string | number | Date

export interface IMark {
    type: string
    name: string
    value: number | null
}

export interface IResourceKV {
    [namespace: string]: {
        [key: string]: string
    }
}

export interface IAsset {
    id: IDString
    type: string
    role: string
    mime: string | null
    extension: string | null
    is_external: boolean
    is_primary: boolean
    is_on_uploading: boolean
    url: string | null
    derived_from: IDString | null
    created_at: Timestamp
    updated_at: Timestamp
    data: Record<string, unknown> | null
}

export interface IResourceData {
    id: IDString
    created_at: Timestamp
    updated_at: Timestamp
    locked: boolean
    hidden: boolean
    is_deleted: boolean
    title: string
    description: string | null
    parent_id: IDString | null
    order_index: number
}

export interface IResource {
    data: IResourceData
    assets: IAsset[]
    marks: IMark[]
    kv: IResourceKV
}

export interface IResourceChildRef {
    id: IDString
    order_index: number
}

export interface IResourceTreeView {
    resource: IResource
    children: IResourceChildRef[]
}
```

### Пояснення до контрактів

* `IResource` є канонічним доменним агрегатом ресурсу
* `IResourceTreeView` є проєкцією для сценаріїв, де потрібно явно показувати дочірні ресурси
* `children` винесено з базового контракту Resource, щоб не змішувати джерело істини і похідне представлення

# 8. Що свідомо винесено за межі цього документа

Наступні теми не входять до чистої предметної моделі і мають бути описані окремо:

* як працює Core
* як організований storage driver
* як реалізуються модифікаційні операції
* як забезпечуються атомарність, узгодженість, ізольованість та довговічність
* як працює журнал операцій
* як синхронізуються зовнішні зміни стану сховища
* як працює система плагінів
* як формуються фасади публічного API

Це потрібно для того, щоб предметна модель залишалася стабільним описом сутностей і правил, а не змішувалася з деталями виконання.
