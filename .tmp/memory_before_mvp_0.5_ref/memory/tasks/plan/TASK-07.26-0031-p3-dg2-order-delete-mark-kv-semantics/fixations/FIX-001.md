## Exact changes proposed

### Hierarchy/order

- Active sibling group includes only `is_deleted = false` Resources with exact common `parent_id`.
- `order_index` is non-negative safe integer and active group permutation `0..n-1`.
- Stored graph remains existing/cycle-free; active child requires active parent.
- `moveResource(id,{parent_id,order_index})` uses insertion semantics after target removal; range `0..destinationCount`; no clamping.
- Move stages target and only siblings whose parent/order actually changes, sorted by Resource ID for fingerprint/journal; no-change has no transaction.
- New create root uses `order_index = activeRootCount` after P3-VS3.
- Coarse `resource-hierarchy` lock avoids stale sibling lock plans and lock acquisition under storage session.

### Delete/restore

- Delete only active Resource without active children.
- Effective delete preserves tombstone parent/order/flags/aggregates, sets `is_deleted = true`, bumps target timestamp and densely reindexes changed active siblings.
- Default query/tree hides tombstones; delete success returns one detached tombstone snapshot.
- Repeated delete returns `RESOURCE_ALREADY_DELETED`; active children return `RESOURCE_HAS_CHILDREN`.
- `locked`/`hidden` neither block nor change.
- Restore/include-deleted/purge/cascade are deferred and absent from public Phase 3 surface.

### Marks

- `setMarks(resourceId, marks)` fully replaces canonical sorted Marks; empty clears.
- Exact ordinary descriptor-safe objects; `type`/`name` nonblank exact strings length `1..128`; value null/int32; max 256; duplicate exact identity invalid.
- Sorting uses binary ECMAScript `(type,name)` order; identical replacement returns `RESOURCE_NO_CHANGES`.

### KV

- `setKV(resourceId, namespace, values)` fully replaces one namespace; empty deletes it.
- Namespace/key nonblank exact strings length `1..128`; max 256 keys/namespace and 256 namespaces/resource; values max 16384 code units; resulting total max 1,048,576 code units.
- Mapping equality ignores property insertion order; fingerprint serialization sorts keys.

### Protocol/API

- Extend operation/journal types with `resource.move`, `resource.delete`, `resource.marks.set`, `resource.kv.set`.
- Rename pre-session plan `affected_resources` semantics to non-authoritative `resource_hints`; after coherent load handler builds immutable `PreparedResourceWriteSet`. Journal `affected_resources`, changes, staging і fingerprint use only exact sorted prepared IDs/snapshots; locks are not replanned under session.
- Extend prepared index seam to atomic batch upsert and active visibility validation.
- Add `MoveResourceInput`, `SetMarkInput`, `moveResource`, `deleteResource`, `setMarks`, `setKV`, compile-valid per-method error unions and exact precedence from detailed report, all `experimental-phase-3`.
- Add `STORAGE_INTEGRITY_FAILED` to exact existing `ResourceWriteError` and all new per-method unions, plus `operation` to public `SafeDiagnostic.stage`. Detected pre-commit durable/index invariant defects return normalized current result, safe diagnostic, engine intake close, facade unpublication, Module failed, no same-instance restart; fresh composition must recover/revalidate before ready. Post-commit faults retain committed warning semantics.
- Materialize internal `ResourceRuntimeIntegrityError` classification in driver/index adapters, `OPERATION_INTEGRITY_FAILED` engine result and lifecycle-owned no-throw `RuntimeFaultPort`; engine close і fault-port unpublication виконуються в одному synchronous no-await turn до async cleanup, тому cleanup-window calls вже отримують `MODULE_NOT_READY`. Ordinary acquire/I/O failures remain lock/write failures. P3-VS3 owns implementation, delayed-cleanup race proof та injected acquire/read/index verification, including existing create/update mapping.
- Preserve readonly-before-inspection, committed `ResourceWriteSuccess`, warnings/fail-close, opaque driver and no public transaction/Core/IoC.

## Architecture pressure

Proposal preserves one Core write port, Operation Engine, driver semantic commit, committed-only journal and prepared index publication. Coarse hierarchy lock is deliberate bounded serialization, not a second authority. Stop conditions remain facade-direct driver/index/journal access, partial sibling commit, index-as-authority, locks acquired under session, public transaction/Core/IoC or Asset/hooks/sync leakage.

## Risks

- Experimental existing root create order is refined; persisted pre-gate migration remains outside current durability promise.
- Coarse hierarchy lock may require later performance refinement, but not for correctness.
- Leaf-only delete and deferred restore are intentionally narrower than possible future product semantics.
- Mark/KV limits become compatibility-relevant after application/public freeze.
