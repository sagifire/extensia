### Generic internal lifecycle contribution contract

- Immutable descriptor має форму capability-level contract: `id`, `order`, `start(): Promise<void>`, `stop(): Promise<void>`; exact TypeScript naming internal і не є public commitment.
- `id` — lowercase ASCII safe identifier довжиною 1..128 за pattern `^[a-z][a-z0-9]*(?:[.-][a-z0-9]+)*$`; ID унікальний у fresh composition і валідований до першого `start()`.
- `order` — safe integer. Startup виконується sequentially за ascending tuple `(order, id)`; duplicate order дозволений, ordinal ID є deterministic tie-breaker.
- Validation сканує contributions у deterministic registration order до resource starts. Invalid ID/order і duplicate valid ID формують ordered validation entries; unsafe invalid ID не копіюється в diagnostics, optional ID omitted.
- `start()` contribution зобов'язаний локально прибрати власне partial acquisition до reject. Controller не викликає `stop()` для contribution, чий `start()` не resolved successfully.
- Cleanup ledger додає descriptor тільки після resolved `start()`. Для кожного ledger entry `stop()` викликається at most once; stop attempt, навіть rejected, закриває entry без автоматичного retry.
- Lifecycle contribution не реєструє той самий active resource як окремий IoC disposer. `stop()` володіє active-resource cleanup; composed-runtime `dispose()` володіє graph/provider disposal. Це запобігає double cleanup.
- Fake storage-shaped fixture реалізує цей generic descriptor лише як test fixture; його fields/behavior не оголошують Storage Driver methods, capabilities, durability або future integration API.

### Exact internal lifecycle state, cleanup і result policy RUN-001

- Internal states: `created`, `starting`, `started`, `stopping`, `stopped`, `failed`; names не є public compatibility commitment.
- Composition/construction може створити graph/objects, але не запускає active resources і не публікує internal ready state.
- `start(created)` запускає ordered lifecycle resources; `start(started)` повертає idempotent success.
- `start(starting|stopping)` повертає normalized internal `LIFECYCLE_BUSY`; `start(stopped|failed)` повертає `LIFECYCLE_INVALID_STATE`; restart/retry не підтримується в baseline.
- `stop(created)` виконує composed-runtime disposal без contribution start і переходить у `stopped`; `stop(started)` очищає ledger у reverse startup order, виконує disposal і завершує у `stopped`; `stop(stopped)` є idempotent success.
- `stop(starting|stopping)` повертає `LIFECYCLE_BUSY`; operation waiting/cancellation не входять у baseline.
- Startup failure спершу фіксує primary `LIFECYCLE_START_FAILED`, запускає reverse cleanup тільки ledger entries з resolved starts, потім composed-runtime disposal; final controller state — `failed` до explicit `stop()`.
- `stop(failed)` не повторює rollback, contribution stops або disposal: він лише переводить controller у `stopped` і повертає idempotent success; попередній failure aggregate лишається в safe inspection history.
- Normal stop і rollback намагаються очистити всі applicable ledger entries у reverse order; одна failure не short-circuit решту cleanup. Stop attempt позначається виконаним незалежно від resolve/reject.
- Один internal lifecycle host володіє composed-runtime disposal і викликає його at most once. Dispose attempt позначається до await, тому rejected dispose не повторюється через `stop(failed)` або повторний `stop(stopped)`.
- Startup failure aggregate має deterministic order: primary start failure; cleanup failures у фактичному reverse ledger order; runtime dispose failure останньою. Normal stop aggregate: contribution stop failures у reverse ledger order; dispose failure останньою.
- Failure entries містять тільки Extensia-owned codes `LIFECYCLE_VALIDATION_FAILED`, `LIFECYCLE_START_FAILED`, `LIFECYCLE_STOP_FAILED`, `RUNTIME_DISPOSE_FAILED`, `LIFECYCLE_BUSY`, `LIFECYCLE_INVALID_STATE`, safe contribution ID і stage. Raw messages, causes, instances та config values не копіюються.
- `start()` failure повертає failure aggregate і state `failed`. `stop()` завжди завершує state `stopped`; якщо stop/dispose мав failures, повертає normalized failure aggregate, інакше success. Повторний `stop(stopped)` повертає success, а попередня diagnostic history лишається inspection-only.
- Descriptor validation failure виконує composed-runtime disposal at most once і переходить у `failed`. Aggregate order: validation entries у registration order, optional dispose failure останньою. `stop(failed)` після цього не повторює disposal й лише переводить state у `stopped`.
- Internal ready/started публікується тільки після success усіх required stages; partially initialized capabilities не вважаються ready.
- Fresh composition per scenario; mutable post-compose override заборонений.
- Tests обов'язково покривають: contribution, що сам очищає partial acquisition і rejects; controller не викликає його `stop()`; ledger inclusion лише після resolved start; cleanup reject без short-circuit; dispose reject; deterministic aggregate order; at-most-once stop/dispose; `stop(failed)` без повторного cleanup; duplicate/invalid ID/order pre-start failure.
