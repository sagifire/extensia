## Спільні правила набору

- Усі шість tasks створюються зі статусом `backlog` без `RUN-*` або `RSCH-*`.
- Activation order: `BP2-01 -> BP2-02/BP2-03 -> BP2-04 -> BP2-05 review-ready -> BP2-06 -> human gate Phase 2`.
- `BP2-02` і `BP2-03` можна активувати окремо та виконувати паралельно лише після task-level human approval `BP2-01` та завершення окремої owner task `interactive-memory-update`, яка застосовує погоджену людиною design fixation до canonical memory і фіксує ID application artifact/task.
- Підготовка задач не є погодженням design alternatives, exact signatures, API stability або config shape.
- Conceptual signatures source specifications є input для design, а не authority для public freeze.
- Жодна Phase 2 task не може повертати successful write, створювати journal/write foundation або розкривати raw IoC/Core.

## Canonical task BP2-02 / TASK-07.26-0016

Назва: `BP2-02 — Реалізувати read-only Core Extension Port і minimal index`.

- Status/type/mode: `backlog` / `feature` / `autonomous-implementation`.
- Мета: побудувати найвужчий internal read path `readonly driver -> Core read port -> minimal Resource index`, потрібний accepted BP2-01 contract і BP2-04.
- Обсяг: production-owned readonly driver port/fixture binding; deterministic fixture loading; мінімальні Core read requests; Resource-by-id і parent-to-children projection; minimal greedy initialization; validation missing/invalid/cyclic/orphan fixtures за погодженим contract; detached JSON-safe readonly snapshots; lifecycle startup/failure/cleanup; internal diagnostics без leakage.
- Поза обсягом: public facade/registry implementation, Extensia Module public surface, writes/journal/locks/recovery/sync, Asset/Mark/KV/global search, lazy completeness claims, concrete durable driver.
- Залежності й активація: BP2-01 `done`; окрема owner task `interactive-memory-update` застосувала погоджену design fixation і зафіксувала stable application task/artifact ID зі спільною internal read-port/adapter seam; BP1 domain/composition/lifecycle accepted; окрема явна activation створює `RUN-001`. Може виконуватися паралельно з окремо активованою BP2-03.
- Критерії приймання: погоджений read contract реалізований без speculative methods; `children` виводяться лише з `parent_id`; поведінка missing/invalid/cyclic/orphan точна; snapshots detached й immutable by contract; немає journal/write dependency; driver objects не витікають; initialization failure виконує rollback/dispose; fresh compositions isolated; немає public exports поза погодженою boundary.

- Синхронізація пам'яті: factual current domain/technical implementation, task/run artifacts, indexes/state за фактичним статусом; public target changes лише через погоджену BP2-01 fixation.
